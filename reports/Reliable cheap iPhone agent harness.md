# Give Mode's hands eyes, memory and brakes

Mode's agent does not get stuck because Haiku 5.5 is too weak or because the screenshots are unreadable. In every failed or looping run audited, the fact the model needed was visible in the screenshot. The harness's text channel dropped it, the loop guards could not see the loop, or the one affordable escalation had already been spent. Specifically: nothing said "keyboard up, field focused", so Haiku tapped a focused Swiggy search field six times. OCR fragments with no card grouping hid which restaurant had which rating, so it scrolled up and down ten times. The guards count only byte-identical "unchanged" screens after phone actions, so refused plans and same-page taps never added up to a stop. The open-source harnesses that succeed (minitap mobile-use, Mobile-Agent-E, Agent S3) all do the same few things. They handle focus and typing in code, verify every action against before/after state, keep a scratchpad of options seen across screens, apply hard loop rules that escalate to a stronger reasoner, and target elements rather than raw pixels. In minitap's ablation, post-validation alone was worth 15 points and the scratchpad 8. Mode can adopt almost all of this without an accessibility tree, and without changing models. The fixes are generic "hands" and "eyes", so they keep the no-hard-coded-tasks rule. The highest-value changes are small and local: keyboard detection with a self-focusing `type_text`, a tolerant `settle()` (wait time is now the largest single block of wall time), one progress meter that escalates and then stops, and escalation spent on real decisions. Together they address every failure mode in the logs. The audit estimates a 30–50% cut in steps and a 40–60% cut in latency at the same or lower cost, but these estimates are unmeasured until a bake-off confirms them.

*Evidence base.* Code references point to HEAD `fb11ebc`, with files under `engine/agent/src/commonMain/kotlin/com/piyush/mode/agent/` unless another path is given. Run IDs (for example "run 14-11-27 S3") refer to the 35 runs from 2026-11-01 in the session's `phone-test/logs/runs/` folder. Web sources are linked inline.

## Every failure had the answer on screen, and the text channel dropped it

The audit traced six failing or looping runs step by step. The pattern is consistent. The screenshot held the information, but the OCR list that the rules tell the model to rely on ("use its listed centre") lost it, and nothing else carried the missing state.

| Run | Symptom | What the screenshot showed | What the text channel gave the model | Why the loop continued |
|---|---|---|---|---|
| 14-11-27 Swiggy (Haiku) | Tapped "Focus search field" 6× (S3–S8) | Caret, full QWERTY, blue Search key; by S6 the iOS "Paste \| AutoFill" callout | 54 OCR boxes, 23 of them keyboard keys; the placeholder "Try 'Pizza'" looked like an empty field and rotated to "Try 'Biryani'" | "Same page" taps still passed `changed = true` to StuckDetector (`Agent.kt:264-274`), so `unchanged` never rose |
| 14-01-05 Swiggy (Haiku) | Sorted by rating, then scrolled up/down 10× and re-planned 6× (S8–S30) | Cards with ratings, an "AD" card at 4.7, the top card's name under a sticky header | Vision-order OCR: "I UNI" for "Yuki", "AD" labels and offers as separate boxes | One reversal hold (S12); the same reversal went through at S13; a $0.0265 Sonnet step-up also just scrolled |
| 14-05-46 Swiggy (Haiku) | 16 consecutive `plan` calls (S15–S30) | Same list | SEEN WHILE SCROLLING held "Yuki 4.6 (2.3K+)", "Noodle Bar 4.6 (2.0K+)", "WeFit 4.7 (186)" as flat lines | Plan refusal → `critical()` → step-up verdict reset `plans = 0` even though the Agent declined the step-up on budget, so plans alternated "saved / not saved" |
| 13-50-30 Swiggy (Qwen) | Off-screen taps; 9 of 11 "Add Item" taps held back (S15–S25) | "Add Item \| ₹455" at (301, 934) | Pixel centres on a 460×1000 image | Qwen sent 0–1000 normalized x (659 → 303 px). A missed "Adding…" tap became a pending ChangeLedger entry that blocked every retry |
| 12-42-09 MyFitnessPal | "Food logged!" 5 times | "+" icon with no text | `tap (410, 340)`, no label | Before the ChangeLedger; reasons like "Verify: check Dinner log" while tapping add |
| 13-22-48 MyFitnessPal | Scroll down/up 6× looking for Snacks | "Dinner" at the bottom, Snacks further down | No end-of-list or "keep going" signal | A memory fact ("usually already in the Snacks section") was wrong for today |

Three information gaps explain almost all of this.

**The first is state.** iOS shows a focused field through the keyboard and a caret. Mode's OCR turned that into twenty stray letters. On the 40 of 339 screen-bearing steps with the keyboard up, those letters averaged 20.6 of about 33 boxes, and there was no "KEYBOARD IS UP" line. The prompt then pushed the wrong way: the rule "Tap a text field before typing into it" (`Agent.kt:829`) and the `type_text` description "tap the field first" (`AgentTools.kt:108`) reward another tap.

**The second is structure.** OCR boxes arrive in Vision's order, capped at 80 and unsorted (`ContextBuilder.kt:166`). A card's name, rating, rating count and "AD" flag come apart. Haiku cannot reliably rebuild "Matsuri 4.7 (106) vs Yuki 4.6 (2.3K+)" from that, even when the data is in SEEN WHILE SCROLLING, which is a de-duplicated run of lines, not cards.

**The third is convention.** The action space is raw screenshot pixels, so each model's coordinate habit becomes a correctness issue. Mode's out-of-range check (`AgentTools.kt:252-260`) cannot catch normalized values that happen to fall inside 0–460.

minitap's paper reports the same mechanism from the other side. In its single-agent baseline, the largest failure class was "text input failures where the agent believed input succeeded" (12 of 42). The fix there was to move focus, cursor and keyboard handling into deterministic code ([arXiv 2602.07787](https://arxiv.org/html/2602.07787v1)). MobileWorld lists the other half: repeated actions from forgetting completed work, and logic errors when comparing items ([arXiv 2512.19432](https://arxiv.org/html/2512.19432)).

Memory made two runs worse. A stale tip ("KOKO 4.4 … Daily Sushi 4.4") was copied into a Qwen note as fact (run 13-30-58). A wrong "usually in Snacks" fact sent the model looking for Snacks (run 13-22-48). Swiggy prompts also carried unrelated WhatsApp and MyFitnessPal facts and five "could not finish" history lines (run 14-11-27). The brief, which is supposed to anchor the plan, failed silently in 3 of the last 8 runs. Sonnet was paid about $0.015 and took up to 9.8 s, then `parse()` rejected the arguments and the error was logged as "unknown" (`Brain.kt:62-63, 121-124`). With no brief, the `plan` tool came back.

## The guards count the wrong thing and spend escalation on trivia

Mode's loop protection grew one incident at a time, and the pieces now work against each other.

**StuckDetector counts only one kind of non-progress.** It counts exact-signature "unchanged" screens after a phone action (`StuckDetector.kt:39-80`). A rotating placeholder, a blinking caret or 2–4 px of OCR jitter defeats signature equality. The "visits" counter needs identical signatures, so it fails the same way. Non-phone steps (plan, recall, a held-back action, a refused `done`) set `changed = null` and never count at all. That is how run 14-05-46 burned 16 straight steps on `plan`, and how run 13-50-30 burned 9 on held-back taps, without the detector firing.

**The step-up path makes this worse.** `stepUp()` resets `plans`, `waits`, `badReplies` and `sinceStepUp` and sets `steppedUp = true` unconditionally (`StuckDetector.kt:124-131`). The Agent separately declines the step-up when `maxCostUsd − cost ≤ 3 × lastStrongCost` (`Agent.kt:297-298`). Under the $0.10 default cap, one brief (about $0.015) plus one Sonnet step (about $0.025) already exhausts that headroom. Each declined escalation therefore still wipes the counters that should have stopped the run.

**`critical()` spends the single affordable strong step too early.** It fires from about seven places: plan refusal, the first look at a pending ledger entry, ask_user after any ledger entry, ADD_IS_NOT_A_CHECK, confirmed repeats, and held-back actions (`Agent.kt:287, 393, 415, 476, 482, 488`). In the logs the Sonnet step-up went to typing "sushi" ($0.0252, 55% of run 14-05-46's cost), to `open_app MyFitnessPal` ($0.0092, run 13-22-48), and to a wrong promo tap ($0.0080, run 13-04-40). Sonnet steps are sent uncached on purpose (`Agent.kt:324-325`) and cost 25–80× a cached Haiku step ($0.0003–0.0004). The only fully successful Swiggy-class run, Zomato 13-04-40, succeeded because three Sonnet step-ups did the hard taps (open YUKI, ADD, "Add item") while Haiku only navigated. That run is also evidence that the strong model is being used as a fallback executor when it should be a judge.

**The ChangeLedger solved duplicate adds and created a deadlock.** It classifies a "change" from English verbs in the model's `reason` (`Changes.kt:10-40`). So "Open Dinner log to add food" on a "Log" tab counted as a change (run 12-42-09 S4). A change-tap that missed, because of Qwen's off-screen x, stayed pending, and every later attempt was "held back: first check your change at step 14" (run 13-50-30). The same rule blocked Sonnet's correct ADD at S10.

The open-source projects use fewer, simpler rules:

- **Mobile-Agent-E** ends a run after the same action more than three times in a row (Swipe and Back excluded) or after three consecutive errors. After k = 2 consecutive verified failures, the Manager revises the plan. With GPT-4o these rules cut the termination-error rate from 52% to 32% ([arXiv 2501.11733](https://arxiv.org/html/2501.11733)).
- **Agent S3** removed its manager entirely. It gained 8.8 points on OSWorld and halved LLM calls per task (73.6 → 35.1). Its worker can re-plan locally, and nothing re-plans on a schedule ([arXiv 2510.02250](https://arxiv.org/html/2510.02250)).

That is a direct argument for deleting Mode's `plan` tool. `plan` accounted for 71 of 368 decisions (19%), and 16 of those were refused.

## Waiting for the screen to settle costs more than the model

Across the 35 runs, "act" time totalled about **1,205 s**, more than **1,166 s** of LLM time and **339 s** of looking. A tap's median act time is **4.1 s (p90 8.7 s)**, though the touch itself takes about 50 ms. The cause is `settle()` (`Agent.kt:594-610`). It waits 400 ms, then takes 2–7 "tiny" captures 150 ms apart until two are byte-identical. Each tiny capture is a full-resolution PNG screenshot over a freshly reconnected ScreenCapture service, shrunk to a 160-px JPEG (`CoreDeviceBackend.kt:138-155`; `native/modecore/src/session.rs:283-295`). After that, `look()` takes yet another full capture. A blinking caret or a rotating placeholder never produces two identical frames, so the focused-search-field taps in run 14-11-27 cost **8.5–9.1 s each**, against 1.8–2.6 s on static screens.

The brief adds 7.5–9.8 s before the first action. Taps classified as changes add another 1.2 s of `flashed()` captures. Haiku itself is fast: median **2.05 s** per decision, against Sonnet's 4.0 s and Qwen's 6.8 s (p90 21.3 s, max 33.6 s). Qwen's latency alone rules it out as "hands", whatever its benchmark score.

The prompt is not the speed problem, but it carries noise. The median decision sends **9,616 prompt tokens**, of which a cached ~10.3k-token prefix holds the 9,747-character rules, 16 tool schemas and memory. Only about **1,725 tokens** are uncached per step. Inside that per-step part, unsorted OCR, keyboard keys and refusal messages repeated for up to 12 history lines dominate. During run 13-50-30's held-back streak the per-step text grew from 6.4k to 10.8k characters. Mobile-Agent-E's perceive-reason loop ran 27–41 s per operation ([arXiv 2501.11733](https://arxiv.org/html/2501.11733)), and minitap averaged 31 s per task partly because it chose a low-level controller over frameworks that add 600–1,400 ms per action ([arXiv 2602.07787](https://arxiv.org/html/2602.07787v1)). Mode's CoreDevice path is already that kind of low-level controller. The waste is all in Mode's own stillness check.

## Reliable harnesses verify, take notes and target elements

The 2026 leaderboards are noisy. AndroidWorld claims of 91–100% are mostly vendor self-reports, and AndroidWorld is saturated ([AskUI benchmarks](https://www.askui.com/benchmarks); [BenchLM AndroidWorld](https://benchlm.ai/benchmarks/androidworld)). On the harder MobileWorld benchmark (201 tasks, 62% multi-app, 27.8 average steps), the best harness reaches about 52% and end-to-end GUI models reach at most 21% ([arXiv 2512.19432](https://arxiv.org/html/2512.19432)). That is the realistic ceiling for consumer apps like Swiggy. The design lessons hold up better than the scores. The best-documented ablation is minitap mobile-use (open source, Apache-2.0, a self-reported 116/116 on AndroidWorld):

| Component removed (minitap) | Points lost | Mode's equivalent today |
|---|---|---|
| Multi-agent architecture | 21 | Haiku hands + Sonnet brain, but the brain is used mainly as a fallback executor |
| Post-validation (verified execution) | 15 | Only "screen changed / same page / unchanged" plus flash proofs for adds |
| Sequential execution (abort the batch on failure) | 12 | One action per step; no composite actions |
| Hybrid perception (structure for targeting, image for context) | 11 | Screenshot + unstructured OCR; no elements |
| Meta-cognitive reasoning (cycle detection, strategy check) | 9 | Heuristic StuckDetector |
| Scratchpad memory | 8 | NOTES plus the flat SEEN WHILE SCROLLING |

Source: [arXiv 2602.07787](https://arxiv.org/html/2602.07787v1). The paper's abstract says +7 for verification while the table says 15. That inconsistency is the paper's, so treat the exact magnitudes loosely.

Each of Mode's failure classes has a proven counterpart:

- **Focus loop → verified text input in code.** minitap focuses by ID, then coordinates, then text. It positions the cursor, types, re-reads the field and returns expected-vs-actual to the reasoner.
- **Re-adding items → a per-action verifier plus a notetaker.** Mobile-Agent-E's Action Reflector classifies every transition as A (success), B (wrong page) or C (no change). Its Notetaker stores task facts such as prices and options from each screen. minitap's "evidence accumulation" step checks what is already done before acting. Agent S3 judges outcomes from an "after" crop taken 3 s later to catch delayed changes, which suits toasts that flash and vanish ([arXiv 2510.02250](https://arxiv.org/html/2510.02250)).
- **List oscillation → notes plus a forced decision.** Record each candidate as a structured entry while scrolling. On reversal or at the end of the list, hand the comparison to the reasoner from notes, not screens.
- **Re-planning → plan only on verified failure (k = 2).** The rest of the time, use a flat loop.
- **Three steps for "tap field, type, enter" → composite actions.** Mobile-Agent-E's "Tap_Type_and_Enter" shortcut saves two perception-reasoning cycles. AppAgentX's learned high-level actions cut task time from 209 s to 91 s and tokens by 47% ([arXiv 2503.02268](https://arxiv.org/abs/2503.02268v2)).
- **Cost → mix models by role, but never downgrade the core reasoner.** minitap cut cost 32% by putting small models on plumbing roles. Swapping the main decision model to an 8B collapsed success to 11.2% ([arXiv 2602.07787](https://arxiv.org/html/2602.07787v1)).

The last point needs care for Mode, because Haiku makes nearly every next-action decision. Anthropic's own numbers put Haiku 5.5 at 72.4% on OSWorld 2.1, against 83.9% for Sonnet 5.5, but at 39.2% against 70.6% on Terminal-Bench 4.0 ([aiidelist](https://aiidelist.com/blog/claude-haiku-5-5-benchmarks)). That matches the logs: Haiku taps well and judges poorly. The answer is not Sonnet on every step, which at about $0.24 per 20-step task is 5–10× over budget. The answer is a harness that removes judgement from routine steps (focus, typing, settling, verification) and routes the genuine judgement moments to the brain automatically.

## iOS gives one overlay-free structured source, and it is not in idevice yet

Element targeting on Android rests on the accessibility tree. On a real iPhone, every mainstream tree source runs an XCUITest runner: Appium/WDA, Maestro, DeviceKit, and idevice's own `WdaClient`. That brings back the "Automation Running" overlay Mode pivoted away from ([Appium troubleshooting](https://appium.github.io/appium-xcuitest-driver/latest/guides/troubleshooting/); [Maestro iOS driver](https://maestro.dev/blog/maestro-re-building-the-ios-driver)). idb's accessibility commands are simulator-only ([idb docs](https://fbidb.io/docs/accessibility)). ViewHierarchyAgent needs a private Xcode entitlement. CoreDevice's own services cover screenshots, HID, apps and display settings, but no UI structure ([idevice core_device](https://github.com/jkcoxson/idevice/blob/89702099f4d7552f704f93b4526756abda319ceb/idevice/src/services/core_device/hid.rs)).

The exception is the accessibility audit daemon, `com.apple.accessibility.axAuditDaemon.remoteserver.shim.remote`. It is a DTX service over the iOS 17+ RSD tunnel, with the same `lockdown.remote.trusted` entitlement as the other shim services ([pymobiledevice3 RemoteXPC.md](https://github.com/doronz88/pymobiledevice3/blob/master/misc/RemoteXPC.md)). It walks the foreground screen in VoiceOver order. Each element returns a caption that combines label, value and traits ("Flashlight, Off, Button, Not Enabled") plus an opaque handle that accepts an "Activate" action ([pymobiledevice3 accessibilityaudit.py](https://github.com/doronz88/pymobiledevice3/blob/master/pymobiledevice3/services/accessibilityaudit.py)).

The research session measured it on an iPhone 17 Pro running **iOS 27.2 (24B119)**. The service is live, the axAudit connection opens in 312 ms, and the walk costs **30–70 ms per element**: 332 ms for the 7 lock-screen elements. That suggests roughly 1–2.5 s for a 25–40-element app screen, running in parallel with the screenshot. The limits are real:

- No per-element frames on devices. Geometry attributes return nothing, and coordinate hit-testing is simulator-only ([go-ios ax_audit.go](https://github.com/danielpaulus/go-ios/blob/main/ios/accessibility/ax_audit.go)).
- The Activate action carries a `task_for_pid-allow` caveat.
- Out-of-process accessibility misses WebViews and some SDK-rendered content.
- The test ran on a locked phone. Whether Swiggy's captions include "Search Field" or "is editing", and whether the inspector auto-scrolls lists, is untested.

idevice has the building blocks (`RemoteServerClient`, `root_channel`, `rsd_checkin`) but no client. A port of pymobiledevice3's module is an estimated 300–500 lines of Rust ([idevice remote_server.rs](https://github.com/jkcoxson/idevice/blob/89702099f4d7552f704f93b4526756abda319ceb/idevice/src/services/dvt/remote_server.rs)).

So axAudit is a strong spike, not a foundation. The foundation is pixels plus OCR, made structured. Three cheap layers get most of the value:

1. **Keyboard detection from the OCR Mode already runs.** Treat the keyboard as up when there are at least 8 single-character tokens in two or more regular rows in the bottom 45% of the screen, plus one of space/return/search/go/done. Add a rule for the 123/ABC/globe bottom row. No published method for detecting the iOS keyboard from a screenshot exists, so this heuristic needs its own precision check, and non-Latin keyboards are untested.
2. **Row and card grouping of OCR boxes,** with set-of-mark numbering.
3. **An optional on-device icon detector** for unlabeled "+" and chevron buttons. On ScreenSpot-Pro, uitag's MIT-licensed YOLO11s (about 18 MB) raised element coverage from 57.3% with Vision alone to 90.8%, and icon coverage from 42.5% to 87.6% ([uitag](https://pypi.org/project/uitag/)). OmniParser v2's `icon_detect_v3` is the other MIT option. The original `icon_detect` weights are AGPL, which matters for an open-source app ([OmniParser v2 card](https://huggingface.co/microsoft/OmniParser-v2.0)). Apple's Screen Recognition detector shows this model class runs in about 10 ms on an iPhone 11 ([Apple ML Research](https://machinelearning.apple.com/research/mobile-applications-accessible)), but it is not exposed to developers.

The case for set-of-marks over raw pixels is model-dependent. In AndroidWorld's 2024 baseline, GPT-4 Turbo did better with the raw tree (30.6) than with SoM (25.4), and Gemini 1.5 Pro did the reverse ([arXiv 2405.14573](https://arxiv.org/html/2405.14573)). For Mode, the main argument is different: element IDs make taps convention-free, tap descriptions exact, and ledger keys stable. It is not a claim of better grounding accuracy.

## Keep Haiku as hands and buy judgement only at decision points

The model evidence supports Mode's current split, used differently. On OpenRouter, Haiku 5.5 costs $0.10/$0.50 per million tokens, has about 10 endpoints, and runs about 2 s per decision without extended thinking. GPT-6 Luna is the same price, but Anthropic reports it at 48.9% on OSWorld against Haiku's 72.4% ([OpenRouter models API](https://openrouter.ai/api/v1/models); [aiidelist](https://aiidelist.com/blog/claude-haiku-5-5-benchmarks)). Qwen3.8-Omni-Flash's AndroidWorld lead (87.1%) comes from its vendor's launch post. It has a single OpenRouter provider, and in Mode it produced 0–1000 coordinates and 21 s p90 latency ([BenchLM model page](https://benchlm.ai/models/qwen3-8-omni-flash)). Holo3.1 (71–79% AndroidWorld, self-reported) is open weights only, which conflicts with zero-setup BYOK ([H Company](https://hcompany.ai/newsroom/holo3.1)).

On grounding, MobileWorld's planner + 7B-grounder setups beat end-to-end models about 2.5× ([arXiv 2512.19432](https://arxiv.org/html/2512.19432)). But Mode's failures are judgement failures, not grounding failures, and a grounder adds an extra round trip per tap. Add one only behind a measured tap-miss trigger.

Coordinates need a per-model adapter regardless:

- **Claude:** absolute pixels on the image it actually sees. Anthropic explicitly advises against 0–1000 normalized coordinates and recommends pre-resizing so coordinates map 1:1. Mode's 460×1000 screenshot already does this ([Claude vision coordinates](https://platform.claude.com/docs/en/build-with-claude/vision-coordinates)).
- **Gemini:** a 0–999 grid ([Google Cloud computer use](https://docs.cloud.google.com/gemini-enterprise-agent-platform/models/computer-use)).
- **Qwen and most GUI specialists:** 0–1000.

Element IDs avoid the issue for any model.

The cost math favours a rare, decisive brain. A cached Haiku step costs about $0.0003–0.0005. A 20-step Haiku task plus 2–3 brain calls comes to about **$0.035–0.046 with Sonnet 5.5**, or about $0.022–0.028 with GPT-6.1 Terra ($1/$5, which OpenAI says is over 3× faster at computer use than its flagships) ([aicatchup](https://aicatchup.com/news/openai-gpt-6-1-terra)). Gemini 3.8 Flash ($0.825/$4.125) is the third brain candidate for the bake-off. Mode's text-only `decide` call (fb11ebc) is the right shape for the brain. The commit message estimates it at about $0.005, against about $0.025 for a full Sonnet vision step. It should take the structured candidate list and return a decisive sub-goal ("open Yuki"), not a re-plan. It has not yet run in any logged session.

The progress meter and the ledger's "no effect" path must cover those incidents before the old code goes, which is why P0-3 and P0-5 come before P1-8.

## Conclusion

The research changes what "make the agent smarter" means for Mode. Better models are not the main lever. Haiku 5.5 already sees well enough, and a Sonnet-every-step design costs 5–10× the budget. The lever is the deterministic layer between the pixels and the model. A focused field, a card with its rating, a list end, and a tap that did nothing are facts code can establish cheaply and the model should never have to infer. Each fact moved from the LLM into code removes a class of loops and shortens every step. That is the same move behind minitap's verified execution, Mobile-Agent-E's reflector and notetaker, and Agent S3's flat loop.

The second implication concerns escalation. Mode's brain is most valuable as a judge that receives a clean, structured candidate table at a choice point. As an emergency executor triggered by a pile of heuristics, it is least valuable. The P0 changes are cheap enough to land and verify on the phone in days. If they bring Swiggy-class tasks to completion, the open questions (axAudit, icon detection, cheaper brains) become optimizations rather than rescues.
